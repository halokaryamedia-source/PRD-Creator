# Rules

## 0. Preserve source provenance

- Keep original source files unchanged inside the active project package.
- Record every source in `state/source-inventory.yaml` before using it as authority.
- Distinguish authoritative project source, supporting material, reference/golden material, and prior generated output.
- A previous generated document may help recover context but does not automatically outrank its underlying source or approved decisions.
- Never silently resolve a material source conflict. If explicit supersession or authority does not resolve it, classify the affected requirement as Blocked and surface the conflict.
- Do not ask the user for information that is already recoverable from available source or approved state.

## 1. Preserve project intent

- Clarify and complete documentation without replacing the original intent.
- Do not silently change gameplay, mechanics, scoring, progression, learning objectives, win conditions, quantities, or runtime behavior.
- Put every design-changing suggestion in Proposal.

## 2. Complete supported gaps

- Fill missing information only when it follows from strong source/context support without changing design intent.
- Keep terminology, constraints, sequence, and scope consistent with source authority.
- Do not invent unsupported facts or mechanics.
- Use Blocked when a reliable completion requires a user/creative-owner decision.

## 3. Approval boundary

- Clarification and Completion may become canonical content when directly supported and non-design-changing.
- Proposal must not enter canonical content or final HTML before explicit approval.
- Blocked items stop the affected required section until resolved.
- Never treat the model's own proposal as approved.

## 4. Canonical content owns meaning

- `work/content.md` is the Flow 3 source of truth for the project document.
- Follow `CONTENT-CONTRACT.md` for document order, role separation, package coverage, scoring/completion detail, and critical information.
- A required page must contain enough local context for its target role to work without reconstructing the project from unrelated pages.
- Do not use polished prose to hide unresolved critical information.

## 5. Rendering projection is derived

- `work/render-data.json` exists only to render `content.md` deterministically.
- It may reorganize canonical content into page/component fields but must not add a new fact, requirement, mechanic, quantity, score rule, or approval.
- When canonical content changes, regenerate the affected render projection before rendering again.
- Never treat render-data as higher authority than `content.md`.

## 6. The Approved Template is fixed

- Clone the Approved Template. Do not recreate its shared presentation shell.
- Preserve its CSS, JavaScript, class vocabulary, controls, sidebar shell, typography, spacing, component styling, responsive behavior, and print behavior.
- Do not redesign, modernize, simplify, or replace the visual system during project rendering.
- Project-specific navigation/page content may be regenerated by `renderer/render.py` using the existing Golden Sample component vocabulary.

## 7. Replace project-specific content only

Project-owned content includes:

- project title/metadata/brand text;
- story/project context;
- gameplay flow;
- global development pages;
- gameplay package count and content;
- Level Design and Developer requirements;
- scoring/completion/reset/handoff content;
- project glossary terms;
- generated navigation/page numbering required by current package count.

Shared template behavior remains inherited.

## 8. Preserve the Gameplay Package

- Production-relevant packages use Gameplay Overview → Level Design → Developer.
- Package type may be Introduction, Objective, Transition, Ending, Stage, Station, or another approved gameplay unit.
- Do not force Aftershock's objective count, characters, mechanics, or page count onto another project.
- Do not remove required role content because the source was incomplete; return unresolved design gaps upstream instead.

## 9. Preserve reading structure

- A reference table remains a table-shaped information structure.
- A chronological flow remains a flow/table sequence.
- Notes remain notes, not hidden inside unrelated prose.
- Match the approved component family and information density without forcing identical word counts.

## 10. No hidden decisions during rendering

Every meaningful rendered statement must already exist in canonical content and be traceable to:

- source evidence;
- supported Clarification/Completion;
- or an approved Proposal/decision.

The renderer may validate structure. It may not decide product meaning.

## 11. Keep outputs minimal

- Produce only files required by the current flow/task.
- Do not revive Archived builder schemas, content-freeze ceremony, release reports, ZIP packaging, or multi-profile infrastructure unless a concrete current need proves they are required.
- `No change required` remains a valid result.
